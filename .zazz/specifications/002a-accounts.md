## 4. Decisions

1. **AUTH-001's key pair** is generated by the service when it starts (`crypto.generateKeyPairSync`, 2048-bit RSA, fake, per run) and the public key is published at `GET /internal/sessions/public-key` (`@Public()`, PEM). Nothing real, nothing persisted.
2. **CRYPTO-003's hard-coded secret**: `LegacyTokenGuard` verifies HS256 tokens with `process.env.VCX_LEGACY_JWT_SECRET ?? LEGACY_FALLBACK_SECRET`, a string committed in the source. The run never sets that variable, so the committed secret is what verifies — the exploit signs with it. Counterparts take the secret from validated configuration.
3. **Session revocation**: a service-level guard refuses a token whose `sid` names a revoked session. A `sid` with no session record is allowed: the API runner and the tests mint tokens whose sessions were never created. The scoped claim is "a revoked session's token no longer works".
4. **Seeded password hashes** are scrypt with a salt fixed per user (derived from the fixed identifiers), so every run loads identical records; runtime paths that create or change a password use a random salt.
5. **PROTO observability**: pollution is observed through the service, by a GraphQL argument the caller omitted gaining a value (`Object.prototype.role`, `Object.prototype.limit`). The two PROTO tests are the last of their file and use different keys.
6. **SSRF-002's observer** is an HTTP stub the test starts on loopback (ephemeral port); the documentation names the lab's own `http://127.0.0.1:3102/internal/health` as the in-lab target. No other service runs.
7. **Rate limit** (`@fastify/rate-limit`, 10/min) is scoped to `POST /internal/sessions/typed`, declared once, in `apps/accounts/src/platform.module.ts`; the test that counts its ten runs in a file of its own (change log, 9).
8. **Documentation reproductions** run against the HTTP/1.1 relay with `RELAY` exported (`http://127.0.0.1:4111` under the builder's port set; `3201` on the defaults) and are recorded in the run log.

## 11. Open questions

None blocking. Resolved during the work, recorded here and in the run log:

- **Where the PROTO observation reads the polluted key** (decision 5 said "a GraphQL argument the caller omitted"). Polluting `Object.prototype.limit` or `.role` crashes class-validator's metadata grouping — `grouped[metadata.propertyName].push is not a function` — on every route that validates a DTO with that field name, before any resolver reads anything: a 500, not a gain. The observation therefore reads the polluted key off the plain object the legacy resume route unserializes (`updateNotificationSettings` pollutes `userId`, `setPreferenceByPath` pollutes `theme` — still different keys, still both "an omitted field gains a value", still the last tests of their file).
- **SSRF-002's in-lab documentation target** (decision 6 named `http://127.0.0.1:3102/internal/health`): the backend services speak HTTP/2 in cleartext, which `node-fetch` cannot fetch, so the named target answers 500, not proof. The documentation reproduces against the lab's own HTTP/1.1 health route (the gateway's); the test observes with its own loopback stub and proves the redirect with a 302 from that stub, as decided.

## 14. Implementation and review change log

Built as specified, with these deviations, each observed while testing:

1. **CRYPTO's tests live in `test/scenarios/auth.int-spec.ts`**, not `crypto-access.int-spec.ts` as the §6 table says. The ACCESS family has that file; CRYPTO's three scenarios were written beside AUTH's in the first scenario slice and stay there. The table's other column entries stand.
2. **ACCESS-004's sink is the raw request body**, not "a DTO without `whitelist`" as the service specification words it: this service's global `ValidationPipe` has `whitelist: true, forbidNonWhitelisted: true`, so no DTO can carry an extra property through — the old editor's route takes no DTO at all and assigns the body property by property. The weakness (caller-named properties written) is the one the scenario names; the counterpart claims are unchanged.
3. **PROTO-002's first counterpart is refused at the transport**: Fastify's body parser rejects a JSON body carrying an own `__proto__` key, so `updatePreferences` cannot even be handed the parsed document (`400, Body is not valid JSON`). The second counterpart (`importSettings`) receives the same text, parses it, and its typed input's transformation drops the key: the preferences answer unchanged. Both are honest refusals for the identical payload; neither is the `BAD_USER_INPUT` the other families show.
4. **FS-002's destination name rides the request's `name` field** (a query parameter), because `@fastify/multipart` strips path characters from the file's own name: an upload named `../x.txt` arrives as `x.txt`. The console's uploader "named the destination itself", which is feature-plausible and carries the traversal.
5. **FS-001 resolves the caller's name against the process's working directory**. In the tests the service runs from `apps/accounts`, so `..%2F..%2Fpackage.json` is the repository manifest, exactly as the table says; under the start command the services run from the repository root, so the same route reaches it as `package.json` (the documentation shows both).
6. **RE-001's payload is twenty-nine `A`s and `!`** (about two seconds steady state, about seven on a cold engine on this machine; thirty runs to minutes). The test asserts the vulnerable mutation takes at least a second and each counterpart answers the same refusal in under one.

Found by the review of 2026-11-27 and closed on the branch by the lead:

7. **The review base moved from `phase-1-foundation` to `main`**, when the scaffolding and trading were merged. `main` was merged into this branch at `ced531a` (merge base `bf180a3`), which brought trading's files with it; scope is read as `git diff origin/main...HEAD`.
8. **The allowlisted avatar fetch takes its allowlist from validated configuration**, `AVATAR_ALLOWED_ORIGINS`, comma-separated, the lab's own fake avatar host by default. Built first with the allowlist fixed in code to that host over `https`, the direction that fetches and stores could not run on loopback, and no test reached it: a protected counterpart whose only exercise was its refusal. `test/avatar-fetch.int-spec.ts` starts the service with the allowlist on a loopback stub and proves the fetch, the stored URL, and three refusals, each with the reason of the rule that refused it, where all three had said "not on the allowlist". The claim is unchanged: the origin is compared as written before any request, and a redirect is not followed.
9. **The typed sign-in's rate limit is declared once.** A `@RouteConfig({ rateLimit })` on the route itself was never read: with its limit set to one, four attempts were answered. It is removed. The proof of the ten moved from the last test of `auth.int-spec.ts` to `test/rate-limit.int-spec.ts`, a service of its own, because the limiter counts every call from the same address and three earlier tests of that file had already spent three of the ten.

Safe operations: all 41 of §7 are built and none was left out, so the ratio stands at 41 safe to 28 vulnerable. Forty are covered by `test/functional.int-spec.ts`; the allowlisted avatar fetch by `test/avatar-fetch.int-spec.ts`, in a service started with the allowlist on loopback (change log, 8).

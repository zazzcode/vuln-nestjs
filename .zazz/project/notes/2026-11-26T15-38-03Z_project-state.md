# Project state

Date-time: 2026-11-26T15-38-03Z (10:38:03, UTC-5).

A deliberately vulnerable NestJS lab that measures the Zazzles SAST, SCA and DAST tools. The [README](../../../README.md) is the overview for readers, [AGENTS.md](../../../AGENTS.md) is the working guidance for agents, and [`docs/`](../../../docs/README.md) is the documentation for readers of the lab. The [project plan](../project-plan.md) is the plan. This note adds what they do not say.

## What is built

Nothing runnable. The repository holds planning and documentation only:

- The project orientation, the plan with eleven phases (0 to 10), the requirements, and the planned catalogue: 72 active scenarios, 5 negative controls, 8 vulnerable dependency pins.
- Nine architecture documents and nine decision records.
- The specification index and template, with no specification written yet.
- README, AGENTS.md, SECURITY.md, the reader-facing documentation, a pull request template.

## Where the work stands

- The work is on the branch `phase-0-plan-and-architecture`, in a pull request that waits for review. `main` holds only the LICENSE.
- The next step is the specification for Phase 1, written on `phase-1-foundation` after the plan is approved.
- No application code, no `package.json`, no lockfile. No dependency is installed, so no advisory in `docs/vulnerabilities/dependencies.md` has been confirmed by an install or an audit run. They were confirmed against the GitHub Advisory Database.

## What waits for the Project Owner

The [open questions](../project-plan.md#10-open-questions) of the plan. Three of them decide the shape of Phase 1:

- Q2, whether the third backend service is wanted.
- Q9, which service uses the Express adapter. The plan chooses `notifications`.
- Q4, which authentication and validation patterns the baseline uses. The plan chooses the established ones.

One repository setting is the owner's decision: Dependabot security updates must be off before Phase 9 lands, or GitHub will open pull requests against every pin.

## What Phase 1 has to prove first

In this order, because each one can change the plan:

1. The Apollo gateway runs on the Fastify adapter and reaches a subgraph through an HTTP/2 fetcher (risk T1).
2. HTTP/2 on `FastifyAdapter({ http2: true })` (T3).
3. The Apollo subgraph on the Express adapter, through `@as-integrations/express5` (T6).
4. TypeORM 1.1.3 against MongoDB with one real entity (T2).
5. `mysql-memory-server` starts within a test timeout (T4).
6. The lab stops cleanly: no engine process and no temporary directory left.

## Two choices the request did not make

- The request asked for at least two backend services and no more than three. The plan proposes three, with `notifications` as the third, because request forgery, template injection and command injection need a plausible home.
- The request allowed one service on Express without naming it. The plan chooses `notifications`, so that the gateway and the money path stay on Fastify with HTTP/2. The alternative, `accounts`, is recorded in question Q9.

A third choice came from the Project Owner during the work: the application is a sample that is run, preloaded with fake data, and shut down. That is now the organizing fact of the [architecture](../../architecture/project.md) and of [ADR-004](../../architecture/decisions/ADR-004-ephemeral-stores.md).

## Environment

- Node 24.21.0, pnpm 12.23.0, corepack 0.40.8, `gh` 2.103.2 signed in as the owner. The repository is public and the owner has admin rights on it.
- macOS on arm64. `mysql-memory-server` 1.18.0 can download MySQL 8.4 for it.
- No database is installed or was started. Packages were downloaded only to read them: into temporary directories, which were removed afterwards, and into npm's command cache for `npx`.

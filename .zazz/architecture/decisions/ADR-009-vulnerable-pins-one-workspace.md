# ADR-009 — Vulnerable pins, one workspace each, guarded by an audit snapshot

**Status:** Proposed in Phase 0, waiting for review
**Date:** 2026-11-26

## Context

The Project Owner asked for older versions of some libraries with published vulnerabilities, so that the dependency scanner has something to find. A pnpm workspace with one package per service (ADR-001) makes it possible to ask a harder question than "is there a vulnerable package": **which service has it**.

## Decision

- Eight libraries are pinned to vulnerable versions, each in **one workspace**.
- Where the lab has a real use for the same library elsewhere, that workspace uses a **patched** version. It is the control.
- Pins are chosen so that they install without running scripts, and so that their advisories are a stable set.
- `tests/expected-audit.json` is the answer key. It is generated by `pnpm audit:update`, and the update refuses to drop an advisory unless it is retired by name.
- A pin is never upgraded. Retiring one is its own change that names the advisory.

The list, with every advisory, is in [`docs/vulnerabilities/dependencies.md`](../../../docs/vulnerabilities/dependencies.md).

## Options considered

| Option | Why not |
| --- | --- |
| An old version of NestJS itself | Two framework generations in one repository do not mix: NestJS 12 is ESM-only and NestJS 11 is not. Shared libraries would have to be built twice |
| The same vulnerable version in every workspace | The scanner finds it, but there is nothing to attribute and no control |
| Libraries with a steady stream of new advisories, such as `axios` and `handlebars` | Each new advisory moves the snapshot. vuln-nextjs leaves them out for that reason, and so does this lab |
| Any release that is malware | Vulnerable code is a scenario. Malicious code is not |

## Consequences

- The audit snapshot changes over time as new advisories appear for pinned versions. Adding them is routine; removing one is not.
- GitHub will flag the pins. Dependabot security updates are turned off for this repository, as in vuln-nextjs (risk R10 in the [project plan](../../project/project-plan.md#9-risks-and-mitigations)).
- Each pin is validated when it is installed (Phase 9). A pin that does not install or breaks its service is replaced by a candidate from the dependency document.
- Two pins have no control workspace, because only one service uses that library (`ejs`, `mysql2`), and one has no corrected version at all (`node-serialize`).

## Verified facts

Checked on 2026-11-26 against the GitHub Advisory Database through its API. Every advisory named in the dependency document was returned for the pinned version, and every control version returned none.
